# База данных: роли, права, резервное копирование

| Файл | Что это |
|---|---|
| `schema.sql` | вся схема, собранная из миграций EF Core (`dotnet ef migrations script --idempotent`) |
| `roles.sql` | роль `electrofix_stats` и права; для Supabase ещё REVOKE у `anon` и `authenticated` |
| `backup.ps1` | полная резервная копия (pg_dump) с удалением старых копий |
| `restore-test.ps1` | проверка восстановления: развернуть копию в отдельную базу и сверить с исходной |

## 1. Роли и права

### Роли PostgreSQL

| Роль | Кто под ней работает | Права |
|---|---|---|
| `postgres` (в Supabase — `postgres.<id>`) | только ElectroFix.Api | владелец всех таблиц, функций и представлений. RLS на владельца не действует |
| `electrofix_stats` | только ElectroFix.Stats | `USAGE` на схему `public` и `SELECT` на 14 представлений статистики `v_stats_*`, `v_master_workload`, `v_revenue_by_month`, `v_work_order_status_counts`. На таблицы прав нет, писать не может ничего |
| `anon`, `authenticated` (есть только в Supabase) | Data API Supabase | все права отозваны, в том числе на будущие таблицы (`ALTER DEFAULT PRIVILEGES`). Сам Data API выключен |

Ещё три защитные меры на уровне БД:
- **RLS включён на всех 17 таблицах, но правил нет.** Владельцу (Api) он не мешает. Любой другой роли, даже если ей случайно выдадут `GRANT`, таблица покажется пустой. Таблицы предметной области закрывает `03_rls.sql`, refresh-токены — миграция `RefreshTokens`, служебную `__EFMigrationsHistory` — миграция `HistoryRls`.
- **У каждого сервиса свой логин и пароль.** Если утечёт пароль Stats, через него можно только читать статистику.
- **Пароли не лежат в коде и в git.** Они хранятся в user-secrets на ПК и в переменных окружения на Render. Подключение к Supabase идёт только по SSL (`SSL Mode=Require`).

### Роли приложения

Роль пользователя хранится в `users.role_id`. Api берёт её из базы при входе и кладёт в JWT, а проверяет через `[Authorize(Roles = …)]` и в сервисах.

| Роль | Что может |
|---|---|
| `admin` | админ-панель: пользователи (блокировка), клиенты, работы, запчасти, журнал аудита, статистика. Деньги, склад и заказ-наряды — только просмотр (требование преподавателя). ФИО клиентов и сотрудников видит скрытыми |
| `receptionist` | записи, клиенты, приёмка, смета, назначение мастера, закрытие, приём оплаты |
| `master` | только назначенные ему заказ-наряды: работа, фактическое время, передача на контроль |
| `purchaser` | склад: приход, выдача по сметам, остатки, движения |
| `client` | только свои устройства, записи и ремонты; согласование своей сметы |

Все изменения пишутся в `audit_log` триггерами: кто, когда, что было и что стало. События безопасности тоже попадают туда: неудачные входы, отказы в доступе, блокировки.

## 2. Регламент резервного копирования

| Что | Как |
|---|---|
| Тип копии | полная логическая копия схемы `public` (`pg_dump --format=custom`): таблицы, данные, функции, триггеры, представления, история миграций |
| Когда | каждую ночь в 03:00, Планировщик Windows на ПК администратора. Если ПК в это время был выключен, копия делается сразу после включения |
| Сколько хранить | 14 дней, старые копии `backup.ps1` удаляет сам |
| Где хранить | `%USERPROFILE%\ElectroFix-backups`, вне репозитория. В копиях есть персональные данные клиентов, поэтому папку нельзя класть в общий доступ и в git (`*.dump` есть в `.gitignore`) |
| Проверка восстановления | каждое воскресенье в 04:00, `restore-test.ps1` на самой свежей копии. Протокол пишется рядом с копиями |
| Журнал | `backup.log` в папке копий. При ошибке скрипт возвращает код 1, и Планировщик показывает задачу как неудачную |

**Почему 14 дней:**
- Покрываются два цикла еженедельной проверки восстановления: даже если одна проверка выявила проблему, есть ещё неделя проверенных копий.
- Ошибку в данных часто замечают не сразу, например клиент приходит с вопросом по закрытому ремонту. Двух недель хватает, чтобы найти копию «до ошибки».
- Одна копия весит около 100 КБ, 14 копий — меньше 2 МБ, место не проблема.
- По 152-ФЗ персональные данные не храним дольше, чем нужно: дальше двух недель копии для восстановления не нужны.

**Почему полные копии, а не «полная + инкрементальные»:**
- Инкрементальные копии в PostgreSQL строятся на журнале WAL: архивирование WAL или `pg_basebackup --incremental` в PG17. Для этого нужен доступ к репликации, а в Supabase на бесплатном тарифе его нет. Восстановление на момент времени (PITR) там — платная опция.
- База маленькая: полная копия делается меньше чем за секунду. Каждая копия самодостаточна, и для восстановления не нужно собирать цепочку «полная + все инкременты».
- Если база вырастет, можно подключить PITR в Supabase. На своём сервере можно настроить архивирование WAL.

## 3. Настройка (один раз на ПК администратора)

Нужен клиент PostgreSQL 17: `pg_dump`, `pg_restore`, `psql`. Скрипты сами находят его в `C:\Program Files\PostgreSQL\<версия>\bin`. Версия клиента должна быть не ниже версии сервера Supabase.

### 3.1. Пароли — в `pgpass.conf`

Создайте файл `%APPDATA%\postgresql\pgpass.conf`. Папки `postgresql` может не быть, тогда создайте и её. Запишите в файл по строке на каждый сервер в формате `хост:порт:база:пользователь:пароль`:
```
aws-1-eu-central-1.pooler.supabase.com:5432:postgres:postgres.<id>:<пароль базы Supabase>
localhost:5433:*:postgres:<пароль локального postgres>
```
- первая строка — для копий с Supabase;
- вторая — для локального сервера, где `restore-test.ps1` разворачивает проверочную базу.

Файл лежит в профиле пользователя Windows и в проект не попадает.

### 3.2. Адрес базы — в переменную окружения

Пароля здесь нет, только адрес. Выполните в PowerShell:
```powershell
[Environment]::SetEnvironmentVariable('ELECTROFIX_DB_URL', 'postgresql://postgres.<id>@aws-1-eu-central-1.pooler.supabase.com:5432/postgres?sslmode=require', 'User')
```
После этого откройте PowerShell заново.

### 3.3. Первый запуск руками

Из корня репозитория:
```powershell
.\db\backup.ps1
.\db\restore-test.ps1
```
Если PowerShell не даёт запускать скрипты, выполните один раз `Set-ExecutionPolicy -Scope CurrentUser RemoteSigned`.

### 3.4. Расписание

Путь к репозиторию поправьте на свой:
```powershell
$repo = 'C:\Учёба\Курсовая\4 курс\Даня\ElectroFix'
$settings = New-ScheduledTaskSettingsSet -StartWhenAvailable

$backup = New-ScheduledTaskAction -Execute 'powershell.exe' -Argument "-NoProfile -ExecutionPolicy Bypass -File `"$repo\db\backup.ps1`""
Register-ScheduledTask -TaskName 'ElectroFix — резервная копия' -Action $backup -Trigger (New-ScheduledTaskTrigger -Daily -At 3am) -Settings $settings

$test = New-ScheduledTaskAction -Execute 'powershell.exe' -Argument "-NoProfile -ExecutionPolicy Bypass -File `"$repo\db\restore-test.ps1`""
Register-ScheduledTask -TaskName 'ElectroFix — проверка восстановления' -Action $test -Trigger (New-ScheduledTaskTrigger -Weekly -DaysOfWeek Sunday -At 4am) -Settings $settings
```
Проверить задачи можно так: Пуск → «Планировщик заданий» → Библиотека. Там видны время последнего запуска и его результат. `0x0` означает успех, `0x1` — ошибку, подробности в `backup.log`.

## 4. Восстановление после сбоя (Supabase)

Порядок действий, если данные в рабочей базе испорчены или потеряны.

1. **Остановить запись.** Render → сервис Api → Settings → **Suspend Web Service**. Так никто не допишет данные в полуразрушенную базу.
2. **Выбрать копию.** Нужна последняя копия до сбоя из `%USERPROFILE%\ElectroFix-backups`. Сначала проверьте её: `.\db\restore-test.ps1 -File <путь к копии>`.
3. **Очистить схему.** Supabase → SQL Editor:
   ```sql
   DROP SCHEMA public CASCADE;
   ```
4. **Развернуть копию** (pg_restore сам создаст схему `public`):
   ```powershell
   & 'C:\Program Files\PostgreSQL\17\bin\pg_restore.exe' --dbname=$env:ELECTROFIX_DB_URL --no-owner --no-privileges --exit-on-error <путь к копии>
   ```
5. **Вернуть права.** Выполните `db/roles.sql` в SQL Editor, как при первой настройке: копия разворачивается без GRANT.
6. **Включить Api.** Render → **Resume Web Service**. При старте Api проверит миграции: история восстановлена вместе с данными, поэтому ничего не изменится.
7. **Сверить.** Запустите `.\db\restore-test.ps1 -Source $env:ELECTROFIX_DB_URL` и проверьте `/api/health`, вход на сайт и в админку.

Шаги 3–4 повторяют то, что `restore-test.ps1` делает с проверочной базой: пустая база, удаление схемы `public`, `pg_restore` без владельцев и прав. Поэтому каждая еженедельная проверка подтверждает и этот порядок.

## 5. Протокол проверок восстановления

| Дата | Источник копии | Размер | Восстановление | Сверка с исходной | Результат |
|---|---|---|---|---|---|
| 24.11.2026 | локальная `electrofix_dev` | 105 КБ | 1,2 с | 17 таблиц и 228 строк совпали; 19 функций, 11 триггеров, 18 представлений, 20 FK, таблиц без RLS 0 | успешно |

Что проверяет `restore-test.ps1`:
- число строк в каждой таблице;
- число функций и процедур, триггеров, представлений, внешних ключей;
- что RLS включён на всех таблицах;
- последнюю применённую миграцию.

Всё это сравнивается с исходной базой. При первом прогоне проверка нашла таблицу `__EFMigrationsHistory` без RLS, это исправлено миграцией `HistoryRls`.
